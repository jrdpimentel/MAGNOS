# Design decisions and trade-offs

Short notes on why things are the way they are, and what I would change.

## 1. The server owns time and money
**Decision:** all billing maths run on the server with the server's clock. Clients only display what the server pushes.
**Why:** a customer PC is untrusted. If the client decided the price or the remaining time, anyone could change it. Server-side billing also survives client crashes and restarts: a restarted client asks the server and gets the running session back.
**Trade-off:** the client shows a locally counted timer between server updates (every 15 s), so it can be off by a few seconds. The server value always wins.

## 2. SQLite
**Decision:** SQLite in a single file next to the server.
**Why:** a café has one server PC and tens of clients, not thousands. SQLite means zero database administration, trivial backups (copy one file), and an installer with no dependencies.
**Trade-off:** one writer at a time and no network access to the database. If this ever served many branches, I would move to PostgreSQL; the EF Core model makes that a contained change.

## 3. SignalR for real-time commands
**Decision:** a persistent WebSocket connection per client (SignalR) for lock/message/chat/state pushes, plus plain HTTP for requests.
**Why:** staff need instant remote lock and chat; polling would be slower and heavier. SignalR also handles reconnects.
**Trade-off:** the client must reconnect forever on a flaky network; I used an infinite retry policy and added server re-discovery when the connection stays down.

## 4. Pricing: tiered rules with pro-rata leftovers
**Decision:** price rules per tier; largest rule first; leftover minutes charged at the smallest rule's rate; whole minutes.
**Why:** it is easy for owners to configure and explain, and it never charges more for less time (covered by a test).
**Trade-off:** sessions under one minute are free. A different rounding policy (round up, minimum charge) would be a configuration option later.

## 5. Plain HTTP on the local network
**Decision:** no TLS by default.
**Why:** certificates are hard for a non-technical owner to set up on a LAN, and the system is meant to stay inside the café.
**Trade-off:** keys and passwords cross the LAN unencrypted. Documented in SECURITY.md; HTTPS is first on the roadmap. Google sign-in requires HTTPS, so it is optional and documented separately.

## 6. Shared secret keys instead of per-user staff accounts
**Decision:** one admin key and one client key, generated by the installer.
**Why:** simple to deploy and understand for a first version.
**Trade-off:** no audit trail of which staff member did what, and the key cannot be revoked per person. Per-user accounts with roles and an audit log are the top roadmap item.

## 7. The lock-down has limits
**Decision:** rely on a Standard Windows account plus policies, a keyboard hook, a watchdog, and read-only program files.
**Why:** a normal program cannot block Ctrl+Alt+Delete or stop an administrator. Pretending otherwise would give owners false confidence.
**Trade-off:** a determined user with admin rights or physical access (Safe Mode, boot media) can bypass it. For higher assurance, use Windows kiosk features or Group Policy on top. This is stated in the README.

## 8. Upgrade-safe database changes
**Decision:** a small `Schema.Upgrade` creates missing tables/columns with `IF NOT EXISTS`, and the installer never overwrites the database or keys.
**Why:** owners upgrade in place and must not lose data. A test builds an "old" database and checks it upgrades with data intact.
**Trade-off:** this does not handle renames or type changes. Real EF Core migrations are on the roadmap.

## 9. Privacy-conscious monitoring
**Decision:** record only the active program name and window title during a session, keep 14 days, and tell the customer on the lock screen and in the widget. No screenshots or keystrokes.
**Why:** it answers "what is this PC used for" with far less risk than screen capture, and respects customers.

## 10. Self-contained packages
**Decision:** publish with the .NET runtime included.
**Why:** café PCs should not need installers for prerequisites. **Trade-off:** larger downloads (about 50 to 70 MB).

## Known limitations
- Plain HTTP; one shared admin key; no audit log.
- Lock-down can be bypassed by an administrator or with physical access.
- No automatic backups (manual copy of the database file).
- Remote desktop and printing are documented using external tools rather than built in.
- Only Windows is supported.
- The member portal's Google sign-in creates new accounts by email; existing accounts are not linked automatically.

## What I would do differently with more time
- Start with per-user staff accounts and HTTPS.
- Use EF Core migrations from day one.
- Put the client's lock-down and session logic behind interfaces so it can be unit tested without a desktop.
- Split the server's `Program.cs` into feature modules earlier.
